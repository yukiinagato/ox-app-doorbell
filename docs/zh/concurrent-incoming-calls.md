# 多路来电：室内机 UI 补充需求

来源：用户在 2026-09-22 追加的需求。优先目标为 iPad / iPhone 室内机。
归属 T36；本设计不代表前置任务、功能实现或设备验收已经完成。

## 现状与目标

AppDelegate 把定向响铃交给当前 IncomingViewController.receive。
现在不同来电会替换尚未接听的来电；已通话时则直接忽略新来电，界面没有等待队列。
这是源码核对结论，尚不是设备实测结论。

改为保留当前选中来电，并显示其他符合本室内机接收条件的来电。
“同一窗口期”按呼叫有效期重叠处理，不增加为了凑齐来电而延迟首次响铃的等待窗口。
只有定向通知本室内机的呼叫可进入来电通知；不能让所有复制到的呼叫都让所有室内机响铃。

## 布局与交互

| 场景 | iPad | iPhone |
|---|---|---|
| 多路待接听 | 主来电/画面与侧边队列；窄竖屏上下排列 | 主来电/画面下方显示紧凑队列和等待数量 |
| A 通话中、B 呼入 | A 的标题和控制区固定；B 显示等待 | A 保持主界面；等待摘要不遮挡操作 |
| 来电多于可见区域 | 显示数量和可访问的完整列表，保持焦点与顺序 | 可展开等待列表，同时保留当前通话控制 |
| 没有有效来电 | 沿既有生命周期返回室内主页或监看 | 同样处理，不留下空来电弹层 |

每条显示门口名称/位置、用途、状态；有可靠来源时显示 Core 时间信息。
没有呼叫开始时间时不编造已等待时长。缩略图标明新鲜度，不代表另一条音频通话。
重名门口要通过位置或稳定标识区分。

首次选中最早的合格来电。后续来电不能悄悄改变接听、开门、回复、挂断的目标。
按钮区域保持稳定；操作绑定激活时的 `(door, call_id, stage_revision)`，再由 Core 校验。
队列条目身份是 `(door, call_id)`，新 revision 更新原条目，不新增一条。

普通来电维持到达顺序，不能每秒按倒计时重新排序。
新来电不移动正在触摸或获得辅助功能焦点的条目。
SOS 保留既有 Core/规则选定的告警优先级，队列不重写全局 SOS 清除或自动取消呼叫。

尚未接听时，用户可以明确选择另一条来电。A 已接通时，选择 B 不得切走 A 的 SIP/媒体目标、
假装支持保持通话，或通过 A 的按钮误开 B 的门。
后端没有合格的保持/多会话能力时，B 保持等待。
“结束 A 并接听 B”必须明确显示两端名称，先完成 A 的既有结束流程，再检查 B 仍可接听，最后接听 B。
若不能验证这个有序过程，就分成“结束 A”再明确“接听 B”，不宣称无缝切换。
A 结束后不能自动接听 B。

本机忽略/静音只作用于本室内机的匹配呼叫，不取消访客或其他室内机。
其他住户已接听、取消、结束、过期事件，只更新匹配身份和 revision。
A 的迟到事件不能关闭 B、删除新 revision 或终止抢答胜者的 SIP 通话。
UI 倒计时不能自行取消 Core 呼叫。

## 提示与资源

采用单一铃声策略，不叠加多个播放器。通话中新来电遵循已有视觉/触觉/短提示配置，不盖过语音。
相同 call/revision 的重复响铃去重；新声音走既有配置与本地化资源流程，不虚构硬件能力。

默认只解码当前选中的合格直播流。等待条目使用文字或有界快照，不为每扇门各开一个实时解码器。
显示画面陈旧/离线状态；权威不可达时，禁用动作并说明原因。
恢复前台或重连时重新核对 Core 状态与接收资格，不直接把保存的旧条目恢复成可操作来电。

覆盖动态字号、VoiceOver、中日英文长名称、对比度、减少动态效果、横竖屏和 iPad 分屏。
有效触控目标至少 44 点。新增等待数量只做一次有意义的播报，不每秒读倒计时或重建焦点。
图标沿用项目 Tabler 资源，不手绘替换。

## UI 实施前必须完成的衔接

当前 `active_calls` 快照不足以表达每个住户的来电通知资格，不能拿全部全局呼叫重建本机队列。
必须先独立记录定向通知的进入资格，再逐条与 Core 的身份和 revision 核对，不能依赖弹层是否已经显示。
恢复前台时只保留仍有效的定向条目；断线期间漏收的通知需要在 T31/T36 中补足权威的、按身份限定的恢复契约。
无法确认资格时显示不可操作的同步状态，不猜测其他住户的范围。

有其他弹窗时，不能先消费响铃事件再丢掉来电。入队、通知和展示分开：页面暂时被遮挡仍保存有效来电，
待可展示时呈现。AppDelegate 和 MainViewController 中现有的铃声播放入口必须共用策略，不能因新增队列再增加一个声音管理者。

接听的异步工作开始前冻结该次操作的呼叫身份与代次。SIP 回调和迟到的 Core 结果只能完成对应的接听操作。
开始另一操作、忽略或切换选择时使旧操作失效；通用 SIP 事件不能把后来恰好选中的条目变成通话中。
必须保留后端抢答胜者校验。

各平台共用队列语义，布局、媒体能力和验收仍按目标分开。Objective-C iOS 5 兼容应用在 T36 下单独实现和验收；
归档的 `ios-legacy` 不加新功能。

## 结束状态与有界的首版方案

| A 状态改变、B 仍等待 | 界面行为 |
|---|---|
| A 取消或过期 | 从待接队列移除 A；按既有规则保留其监看和本机返回计时，禁用通话动作；B 仍需明确选择。 |
| 其他室内机抢答 A | 仅释放本机输掉的通话连接，展示权威结果，不结束胜者；B 继续等待。 |
| 用户结束 A | 结束 A 的精确会话，保留 B，要求明确选择和接听。 |
| 已选择 B 后 A 的监看返回计时到期 | 旧计时不能影响 B 或关闭其页面。 |
| 同一门口发起新呼叫 | 作为新身份处理，不沿用 A 的接听操作、忽略记录或结束计时。 |

手指按下时就冻结动作目标；松手前若选中身份已变化，取消这次点击，不能套用到新条目。
兼容事件缺少身份字段时，必须先与 Core 精确核对，才能删除队列条目或结束会话。

首版等待条目只显示文字：不发缩略图请求、不启用等待条目解码器。默认上限为一个当前选中直播流；
页面退出、后台、内存压力及 SOS 按现有平台策略释放或降级。快照预览要另行明确并验证并发数、字节/像素、
新鲜度和淘汰上限后才启用。

住户会话协调器持有接收记录、本地顺序、选择和通知策略。住户身份改变时废弃旧记录与待完成操作。
更高 revision 要重新确认目标集合；本机忽略只绑定该身份/revision。不完整快照本身不等于呼叫结束。
要宣称完整展示，Core 必须先定义有界、按身份限定的接收/恢复结果；超出容量时须可见，并通过相同权威来源查看，
不能挤掉当前选中或已接通项。元数据保留上限和溢出行为在 T31/T36 按目标冻结和测量，不能拿八路测试当容量证明。

MC-01/11 加入非本住户来电、目标/身份变化及不完整快照；MC-01/07/11/12 加入弹层遮挡及重复通知；
MC-02–06/08 加入接听进行中和迟到 SIP 回调；MC-05/06/08/10 加入取消后监看、同门新呼叫及按下后状态变化；
MC-02/04/06/07/12 检查所有既有声音来源；MC-09/10/12 覆盖溢出、后台、内存和 SOS 转换。
这些是十二项用例的变体，不是额外的运行通过证据。

## 追加验收

以下均为 NOT_RUN，是 T36 的补充场景，不改变原任务编号，也不冒充已有覆盖。

| 编号 | 场景 | 必须观察到 |
|---|---|---|
| MC-01 | A/B 同时待接听 | 两条都可见；初始选中和动作目标稳定 |
| MC-02 | A 通话时 B/C 呼入 | A 连续通话；队列更新；不自动切换 |
| MC-03 | A 响铃时用户选 B | 明确切换选中；动作和媒体均对应 B |
| MC-04 | 其他室内机接听 B | 仅 B 离开等待队列；A 不受影响 |
| MC-05 | 选择 B 时 B 取消/过期 | Core 拒绝旧动作，不回退到另一条呼叫 |
| MC-06 | 同一呼叫更新 revision 后收到旧事件 | 一条新状态；旧回调不改变胜者 |
| MC-07 | 本机忽略 A | 其他室内机及 B 不受影响 |
| MC-08 | A 结束、B 等待 | B 可继续选择；不自动接听或开门 |
| MC-09 | 2、4、8 路重叠来电 | 资源有界；命中区域不重叠；焦点不丢失 |
| MC-10 | 队列变化时旋转/分屏/大字号 | 动作身份和语义位置稳定 |
| MC-11 | 带旧条目恢复前台 | 先核对当前 Core 资格，再允许操作 |
| MC-12 | SOS 与普通来电同时发生 | 保留既有告警渠道、优先级与清除规则 |

测试可以注入 Core 传输/媒体边界，但必须驱动真实队列和控制器。
Core 权威验证、模拟器布局、真实 iPad/iPhone 运行证据分别记录。
设计图和截图不能证明并发处理正确。

## 实施位置

先稳定共享 Bridge 生命周期，再实施 iOS 室内机子任务，并保留 T36 的动作、身份和媒体前置。
队列只是 Core 状态的呈现，不再建立一套 call owner 状态机。
排序/选中逻辑使用实际呼叫身份进行可控测试；UIKit 负责布局；AppDelegate 保留定向响铃路由。
其他室内机平台采用相同语义，分别完成各壳子报告与目标资格验证。

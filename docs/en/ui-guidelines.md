# UI guidelines (cross-platform)

Status: revised 2026-11-12 for the native redesign on branch
`feat/native-ui-redesign` (first adopted 2026-11-06). Every shell is built from
its platform's stock controls and follows that platform's official design
guidance; the shells are not meant to look alike. Behavior, Core contracts, and
the semantic UI manifest stay authoritative; this document decides information
architecture, hierarchy, and which native pattern carries each job.

## 1. Principles

1. **One job per screen.** Each screen has a single primary action that is the
   largest, highest-contrast control. Secondary actions are visibly secondary.
2. **Role decides home.** A door station opens on the visitor screen, an indoor
   panel on the dashboard, a display/monitor on live view. Nothing else competes
   with that home.
3. **Fixed action zone.** Actions live in a fixed bar at the bottom (portrait)
   or right edge (landscape). Content scrolls; actions never move or hide behind
   content, the keyboard, or safe areas.
4. **Same words, same place.** A given action has the same label, icon, color
   role, and position on every platform and every screen it appears on.
5. **Readable at a distance and in three languages.** Layouts must survive the
   longest of ja/en/zh, 200% text size, and a 1.5 m viewing distance on a door
   station.
6. **Native first.** A screen is assembled from the platform's stock controls
   with their default appearance: navigation bars, tab bars, lists, switches,
   sliders, sheets, dialogs. A custom-drawn control is allowed only where no
   stock control can do the job (the SOS slide, the QR viewfinder, live video)
   and it then borrows the platform's metrics, type, and colors.
7. **System look, household accent.** Surfaces, text colors, materials, and
   light/dark come from the platform. Core contributes the effective
   appearance, the accent color, and the semantic roles `positive` and
   `negative`; it no longer paints every surface.

## 2. Size classes

| Class | Width (dp/pt/effective px) | Navigation | Typical device |
|---|---|---|---|
| Compact | < 600 | Bottom tab bar (max 4), drill-down | Phone, iPad 1 portrait split |
| Medium | 600–899 | Navigation rail or tab bar, two columns where useful | Small tablet, portrait tablet |
| Expanded | ≥ 900 | Side navigation, master–detail | Landscape tablet, desktop, wall panel |

Layouts are chosen from the current window size, not the device model, and
switch live on rotation or window resize.

## 3. Tokens

- Spacing, type, and corner radii come from the platform's own scale (Material
  3 tokens, UIKit Dynamic Type text styles and layout margins, Fluent type
  ramp). Where a platform gives no value, use a 4-point grid: 4, 8, 12, 16, 24,
  32, 48.
- Touch targets: at least 44 pt (iOS) / 48 dp (Android) / 44 px (Web, Windows);
  door-station visitor targets at least 72 pt.
- The door-station call button label and the dashboard clock use the
  platform's largest display style.
- Color: use the platform's system colors for backgrounds, text, separators,
  and controls. Core's `accent` becomes the platform accent (Material primary,
  UIKit tint, Fluent accent, CSS `accent-color`). `positive` (answer/connected)
  and `negative` (hang up/SOS/errors) stay fixed semantic roles. Administrator
  overrides addressed to a semantic ID still win on that element, and measured
  low-contrast warnings stay visible in Admin.
- Appearance: follow `display.appearance.effective` from Core; when Core says
  `follow_system`, use the system setting.
- Wallpaper: `display.theme.bg_image` is drawn only behind the home surfaces
  (visitor screen, dashboard, screensaver) with Core's backdrop scrim and
  per-region ink. Every other screen uses the system background. Content over
  the wallpaper sits on the platform's standard card or material.
- Icons: the vendored Tabler set generated by `tools/gen_icons.py`, tinted as
  template images. No hand-drawn glyphs and no emoji.
- Motion: 150–250 ms ease-out for transitions; none when reduced motion is on.

## 4. Screens

### Visitor (door station)

- Top bar: building/door name left, clock center (optional), language switch
  right (flag-free text labels: 日本語 / English / 中文).
- Notice banner below the top bar when an announcement exists.
- Center: purpose cards in a grid (2 columns compact, 3–4 expanded), large icon
  plus label; disabled purposes are hidden.
- Bottom action zone: one full-width primary "Call" button (or "Call without
  choosing" in purpose-first mode).
- States reuse the same frame: calling (pulsing status + Cancel), connected
  (talk indicator + End), reply shown (large reply text, auto-return countdown),
  unanswered (message + Call again). The SOS slide sits in the action zone's
  leading edge only where configured.

### Dashboard (indoor panel)

- Header: cluster clock and status chips (offline devices, SOS state, missed
  calls with badge).
- Door tiles in an adaptive grid (1 column compact, 2 medium, 3–4 expanded):
  live/still preview, door name, last activity, state chip (idle, ringing,
  in call, offline). Tap opens live view; a ringing tile is highlighted.
- Secondary destinations: History, Monitor, Settings via the tab bar or side
  navigation.

### Incoming call

- Full screen, always wins over other screens (see the iOS router).
- Portrait: video top (16:9, letterboxed), door name + purpose + visitor
  language under it, action zone at the bottom.
- Landscape/expanded: video left (≥ 60% width), details and actions in a right
  column.
- Actions, in this order: **Answer** (positive, largest), **Reply** (opens the
  quick-reply sheet), **Ignore** (local only). Secondary row: Monitor/listen,
  Unlock (only when configured), Mic mute in call. In call, **End** replaces
  Answer in the same position.
- Quick-reply sheet: bottom sheet (compact) or popover/side sheet (expanded),
  one tap sends; the call screen stays underneath and alive.

### Live view / monitor

- Video fills the available area; overlay controls auto-hide after 4 s and
  reappear on tap.
- Every live picture (live view, incoming call, in call) can be zoomed and
  moved by touch on every platform: pinch to zoom from 1x up to at least 4x,
  drag to pan while zoomed, double-tap to toggle between fit and 2x. The
  picture never pans past its own edges, and zoom resets when the door or the
  call changes. Pointer platforms also zoom with the wheel and pan by dragging.
  Zoom gestures never trigger or block the call actions.
- Door switcher as a horizontal strip (compact) or side list (expanded).

### History

- Grouped by day; each row: time, door, purpose, outcome icon (answered,
  missed, replied, cancelled), thumbnail when present. Unread missed calls are
  marked; marking seen applies only to what the user has displayed.
- Expanded: list left, detail (snapshot, timeline) right.

### Settings

- Compact: grouped list → drill-down detail with back navigation.
- Expanded: master–detail; left grouped category list with icons and search,
  right grouped inset sections. Row = label + secondary text + native control.
- Destructive or security actions (rotate cluster key, rebuild cluster, remove
  device, factory reset) sit at the bottom of their section, in `negative`
  color, with a confirmation that names the consequence.
- Changes that require the admin window prompt for the admin password once per
  window, never per control.

### Pairing

- Unpaired device: large 8-digit confirm code, device name, and status in the
  center; instructions below; QR when available.
- Adding a device: list of discovered devices → enter its confirm code → result.
- "Re-pair required after upgrade" is a full-width warning state with one clear
  action.

### SOS

- Active SOS: full-screen `negative` overlay that cannot be hidden by other
  screens, source and time, one "Clear" action that needs a deliberate gesture
  (slide or long press) and the admin rules already defined in Core.

## 5. Platform notes

Each table row names the stock control that carries a job. "Home" is the indoor
panel dashboard.

### Android (API 21+, `modern` flavor): Material 3

Material Components for Android with a `Theme.Material3.DayNight` theme; Core's
accent seeds the primary color.

| Job | Control |
|---|---|
| Screen title and back | `MaterialToolbar` top app bar |
| Home destinations | `NavigationBarView` (compact), `NavigationRailView` (medium, expanded) |
| Door tile, history group | `MaterialCardView` |
| Primary / secondary / tertiary action | Filled, tonal, outlined or text `MaterialButton` |
| Settings row | List item with `MaterialSwitch`, `Slider`, or a trailing value that opens a dialog |
| Choice, confirmation, text entry | `MaterialAlertDialogBuilder`, `TextInputLayout` |
| Quick replies, notice editor, history detail (compact) | Modal bottom sheet; side sheet or dialog when expanded |
| Filters and status | `Chip` |
| Transient feedback | `Snackbar` |
| Progress | `CircularProgressIndicator`, `LinearProgressIndicator` |

### Android 4.4 (`legacy19` flavor): framework widgets

The same screens and layouts built from `android.widget` controls under the
Holo device theme: `ActionBar`-style title row, `ListView`, `Switch`,
`SeekBar`, `AlertDialog`, `Toast`. No Material Components dependency.

### iOS and iPadOS (iOS 12+, iOS 9 through availability adapters): UIKit, HIG

| Job | Control |
|---|---|
| Home destinations | `UITabBarController`; each tab owns a `UINavigationController` |
| Screen title and actions | `UINavigationBar` with large titles (iOS 11+), `UIBarButtonItem` |
| Settings, history, device lists | `UITableView`, inset grouped on iOS 13+, grouped before; `UISplitViewController` when expanded |
| Door tiles | `UICollectionView` cells on system grouped background |
| Actions | System `UIButton` (`UIButton.Configuration` on iOS 15+); circular call actions with a caption on the call screen |
| Quick replies, notice editor | Sheet (`UISheetPresentationController` detents on iOS 15+, form sheet or popover before) |
| Admin password, confirmations, choices | `UIAlertController` (alert or action sheet) |
| Filters | `UISegmentedControl` |
| Colors and type | System colors (iOS 13+, a matching static palette before), Dynamic Type text styles |

### tvOS 15+

Focus-driven UIKit: `UITabBarController` at the top, door tiles in a
`UICollectionView` with the system focus effect, system buttons. No answer or
microphone controls.

### iOS 5 kiosk (iPad 1; also iPad mini on iOS 9): stock UIKit 5.1 API

Controls are left to the system to render: the iPad 1 shows the iOS 5 look, the
iPad mini the iOS 9 look. No `UIAppearance` restyling and no palette applied to
stock controls.

| Job | Control |
|---|---|
| Screen title, back, close | `UINavigationBar` with `UINavigationItem` and `UIBarButtonItem` |
| Home destinations | `UITabBar` |
| Settings, history, device lists | Grouped `UITableView` with standard cell styles and accessories |
| Toggles, ranges, choices | `UISwitch`, `UISlider`, `UIStepper`, `UISegmentedControl` |
| Actions | `UIButtonTypeRoundedRect`; toolbar actions as `UIBarButtonItem` in a `UIToolbar` |
| Confirmations, text entry, choices | `UIAlertView`, `UIActionSheet`, `UIPopoverController` |
| Progress | `UIActivityIndicatorView`, `UIProgressView` |

Screens stay `UIView`s swapped by the router (iOS 5 modal presentation is
unreliable); a navigation bar or tab bar is hosted as a plain subview. The A4
budget still applies: no cross-fades, no continuous animation, no offscreen
rendering. Answer, End, and SOS keep their semantic fill because the system has
no colored button there.

### Windows (WPF, .NET Framework 4.8): Fluent

ModernWpf supplies the WinUI control styles and follows the app light/dark
setting.

| Job | Control |
|---|---|
| Home destinations, settings categories | `NavigationView` (left pane when expanded, compact or top when narrow) |
| Settings row | Card row with `ToggleSwitch`, `Slider`, `ComboBox`, `NumberBox` |
| Actions | `Button`, accent-style `Button` for the primary action, `AppBarButton` in a `CommandBar` |
| Confirmations, admin password, editors | `ContentDialog` |
| Quick replies, notice | `Flyout` or `ContentDialog` |
| Status messages | `InfoBar` |
| Progress | `ProgressRing`, `ProgressBar` |
| Lists | `ListView` with the default item container |

Kiosk windows stay borderless and maximized. Targets stay touch sized.

### Web (panel and Admin)

Native HTML controls (`button`, `select`, `input`, `dialog` where supported)
with the system font stack; light and dark through `prefers-color-scheme`
unless Core fixes the appearance; `accent-color` from Core's accent. CSS grid
with media queries for the three size classes, `dvh` and safe-area insets,
usable without hover. Panel pages keep plain fallbacks first for iOS 5 Safari.

## 6. Acceptance

A screen is done when, at compact and expanded sizes and in ja/en/zh at 200%
text, the primary action is visible without scrolling, nothing overlaps or
clips, every target meets the minimum size, and the layout matches this
document. Web is checked with screenshots; native shells list the device/size
combinations still to check on hardware.

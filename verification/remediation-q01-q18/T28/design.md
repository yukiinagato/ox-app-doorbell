# T28 implementation boundary

The existing LWW register overwrites the losing value; neither Store's config rows nor events retain administrator edit intent. Reuse the authenticated Mesh config channel and the existing atomic LwwMap/Store commit callback. Store immutable, content-addressed edit records in the reserved `_config_changes` namespace, excluded from normal config materialization and exports. No new consensus, cipher, transport or executable event is introduced.

Each administrator mutation records a random change ID, author, entity, base entity record digest, all known parent change IDs, typed operations with up to two exact/nearest-ancestor LWW versions per operation, and a redacted candidate snapshot. Entity boundaries are top-level configuration sections, except `devices.<id>`; section granularity conservatively reports concurrent edits to different fields too. Normal edits on an unresolved entity fail visibly. Explicit resolution must reference every current head and replace exactly that entity through the same CAS validation/transaction. Reconnection only transfers records; it never generates a merge write.

The candidate scrubber retains `secret:` references, removes sensitive values, and marks re-entry requirements. Redacted candidates cannot be blindly applied as complete restoration. Credential changes and runtime/bootstrap maintenance retain existing behavior; the journal covers administrator/native configuration mutation endpoints. Mixed fleets retain old LWW behavior and cannot claim full conflict protection for edits authored by unupgraded nodes.

Initial local limits: 512 records total, 64 per entity, 512 KiB encoded records, 64 KiB per record. Remote union reserve: 1024 records, 128 per entity, 1 MiB. A limit rejects the entire local write or remote batch before publication; a persistence/status failure is visible. Records are never discarded by ordinary event or tombstone pruning, including resolved ancestry, until a later coverage-proven retention scheme exists. At capacity further edits are explicitly blocked; this first version does not silently delete history to keep accepting changes.

Tests must execute two real Node instances with production SecureChannel/Mesh/SQLite/CRDT paths over deterministic partitionable transport, with both delivery orders, repeated sync, exact-head resolution, stale/missing head rejection, restart, sensitive fields, limits, and storage failure. Admin conflict rendering and resolution need actual production DOM/browser coverage before closing T28. The current red test checks missing retained candidates through the public native snapshot/commit API.

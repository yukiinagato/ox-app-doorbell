## Findings and requested corrections

- **R1 — remote record validation (accepted by root).** The r4 validator accepted unknown record and operation fields, arbitrary `base_versions`, more than two field parents, and more than 256 operations. Unknown payload can bypass candidate scrubbing and then be stored and exposed as conflict history. The tests construct content-addressed records through the real producer before altering those fields. Root is adding schema, allowed-field, parent-identity, author and count validation.
- **R2 — configuration ingress coverage (accepted by root).** The public native setter, native notice writes/clear, and legacy HTTP import bypassed the journal. Real partitioned native edits and notices lost candidate history; successful HTTP import did not add a record. The tests cover these production entry points and require a blind notice clear to fail while that entity is unresolved. Root is routing them through the same journal transaction. Internal bootstrap/runtime and credential maintenance remain the documented exclusions.
- **R3 — collection-root delete (accepted by root).** Deleting `devices` could create a separate collection entity and bypass `devices.<id>` conflict boundaries. Legacy and CAS deletes must reject the collection root consistently. **The collection-root set was already rejected before T28**; the test preserves that passing baseline. An earlier static suggestion that root set was allowed was withdrawn after checking `configWriteValid(enforce_write_scope=true)`.
- **R4 — partial delete resolution (accepted by root).** A CAS request supplying every `settings` head while deleting only `settings.review` cleared all entity conflicts. The whole-entity requirement was only checked for set operations. The test requires partial deletion to fail unchanged and explicit whole-entity deletion to remain valid. Root is moving the boundary check to the common set/delete path.
- **Additional scrub boundaries (root hardening).** Production tests cover bounded ASCII `secret:` references, malformed/oversized references, and URL userinfo/query/fragment/encoded payload. Valid references must remain references; unsafe payload must become an explicit re-entry marker. Malformed `secret:` values under an otherwise non-sensitive field must not fall through as ordinary strings. These tests are included before the corrected candidate freeze.

## Atomicity and retained-history assessment

The real remote SQLite journal-failure test already passes on r4: after an insert trigger rejects the remote journal, the live configuration revision and effective value remain unchanged; dropping the trigger allows normal authenticated anti-entropy to replay and converge. This exercises LWW frontier rollback rather than only a helper. Static review also checked that the LWW state snapshot includes the version vector, pending sequences, durable remote frontier and local sequence; Store commits config and journal rows together before publication. Reserved journal records are excluded from ordinary materialization/export, and they are non-tombstone immutable records, so ordinary event/tombstone pruning does not delete them.

The deliberately bounded history policy blocks future writes at capacity instead of discarding candidates. It is not a history compaction implementation. Mixed-fleet writes from older Nodes remain outside full protection, as the design states. The corrected r5 production source resolves R1–R4 and the additional scrub boundaries.
